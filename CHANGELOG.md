# Changelog

All notable changes to this project are documented here, in the format of
[Keep a Changelog](https://keepachangelog.com/en/1.1.0/), with [semantic versioning](https://semver.org/).

## [Unreleased]

### Changed

- **CI is waited on just before a module's release commit**, not before the first tag: a module whose CI on `HEAD`
  still runs holds back only the modules that need it, and the run releases the others meanwhile, asking GitHub
  every 30 s, each module up to `ci-wait` from its first ask. A red verdict stops the run there; a stop while it
  waits leaves the run to `resume`, which judges CI again for every module not yet release-committed.
- **The build at new pins compiles the tests too** (`mvn test-compile`): JitPack's `install -DskipTests` compiles
  them, so a test that needs an unreleased upstream change now stops the run before its release commit, not on
  JitPack after the tag.
- **Slow tests are tagged `slow`** and left out of a plain `mvn test` and of CI on Windows; CI on Ubuntu runs them
  (`-Dsluice.excludedTags=`).

### Added

- **sluice-desktop's Releases tab has Resume…** for the newest run that did not finish; it goes on through the
  Release tab, as its own Resume… does.

## [0.5.1] — 2026-11-24

### Added

- **`sluice completion`**: the bash completion script, generated by picocli from the options that parse (zsh through
  `bashcompinit`). The rpm and the deb install it as `/usr/share/bash-completion/completions/sluice`, so Tab
  completes the verbs and their options. A module's alias flag from `sluice.yml` is not offered.

## [0.5.0] — 2026-11-24

### Added

- **`sluice update [--check]`**: this sluice to its latest release, the way it was installed (core's `update`
  package): a jar of the user's replaced; the rpm or deb upgraded from its signed repository by dnf or apt, or without
  it the release's package installed, as root (`sudo` on a terminal, `pkexec` off one); on Windows, once every sluice
  of the install has ended, the MSI's installer run, an unzipped `sluice-windows.zip` unpacked over, or
  `scoop update sluice` run, the last two in a window of their own. Each download is checked against the
  release's new `checksums_sha256.txt` first; a release without one is refused before anything is downloaded.
  `--check` says the installed and latest versions and how it would install. The jar's manifest names the repository
  (`Implementation-URL`).
- **sluice-desktop's Check for updates** (top bar): the same check and update, through core's
  `SelfUpdate.ofWindow`, which replaces a jar of the user's with `sluice-desktop-all.jar` and asks for root through
  `pkexec` even when a terminal started the window. It offers the update only for a newer release, on an install
  it can update. No update starts while a release runs, no release starts while an update runs, and the window stays
  open until the update ends. Off a terminal without `pkexec`, root is asked by `sudo -n`, which never prompts.
- `PinMoves.Goals`: a caller replaces how `versions:set` and `versions:set-property` run (`Goals.maven` the default).
  `Release.Wiring` takes one in place of its Maven arguments.

### Changed

- **sluice takes a verb**: `sluice preview`, `release`, `why`, `resume [--dry-run]`, `status [FILE]`,
  `sync-pins [--dry-run]` and `graph`, each with only the flags it uses (`sluice <verb> --help`). `--execute`,
  `--resume`, `--status`, `--sync-pins` and `--why` are gone: `sluice --all patch --execute` is now
  `sluice release --all patch`, a preview is `sluice preview`, and `--why` is `sluice why`, a preview (a release
  prints no reasons now). `sync-pins` commits unless `--dry-run`. `--module`, a module's alias flag and `--umbrella` stay.
  sluice-desktop's command lines follow, and its resume line no longer carries a dependents flag a resume refuses.
- Core's tests run at once, and the release tests move a plain pom's versions without a Maven run (one end-to-end
  release and `PinMovesTest` keep the plugin under test): the core suite went from 983 s to about 20 s.

## [0.4.2] — 2026-11-23

### Changed

- **A dependent a release owes is released at a patch, not refused.** Releasing `cli` alone, when `core` and
  `studio` pin it, adds both at their next patch, as `--with-dependents` did. `sluice.yml`'s new `owed: refuse` keeps
  the old gate; `--no-dependents` releases only what is named, the dependents keeping their released pins and their
  branch's pin following the release. sluice-desktop's Release tab picks among the three (`owed: as sluice.yml`,
  `--with-dependents`, `--no-dependents`) in place of the *--with-dependents* checkbox.
- `builds-at-pins` builds in a lasting local repository, `sluice/repository` under the user's cache folder (never
  `~/.m2`), instead of an empty temporary one each run, so a preview no longer downloads every dependency again.
  Before each check every snapshot of the umbrella's groups, and every failed download remembered of them, is
  deleted from it: a build at the pins still resolves releases only.

### Added

- sluice-desktop's Release tab says what it adds: a module released because a release owes it shows
  `(added, …)` in *Would cut*, and the status names them with the way to leave them out (`--no-dependents`).
  Execute's dialog lists each refusal `--force` passes over; Resume's names each module's stage and why it
  stopped, and says the request rows are ignored. A row's request is picked from patch, minor and major, or typed;
  the flags wrap, the columns fit the window, and the verdicts scroll.
- **The `ci` gate checks CI on what it releases.** A module ahead of its origin is pushed first (a preview says it
  would), then the gate waits, up to `sluice.yml`'s new `ci-wait` (minutes, default 20, `0` not at all), for a
  finished run of each workflow on its `HEAD`: green passes, red refuses, none by then stays `SKIPPED`. A module
  without a workflow of its own is not waited on.
- **A red run that failed in an upstream is rerun.** When an upstream's CI went green after a module's red run (its
  build reads the upstream's branch), the `ci` gate reruns the run's failed jobs through GitHub's API and waits for
  them like a push; green passes. A preview says it would; a rerun GitHub refuses keeps the refusal, saying why.
- **A run repairs a module behind its origin or with stale pins before it gates.** A module it releases that is
  on its branch with no tracked change is fast-forwarded to its origin, and a pin behind its upstream's `main` is
  moved and committed, as `--sync-pins --execute` does, and pushed by the `ci` gate. The run then decides again,
  and refuses (preview again) when that changes what it would cut. A preview says it would (`clean` and
  `pins-at-main` `SKIPPED`); a diverged or changed tree, or a module the run does not release, is still refused.
- **A module whose upstream the run releases is built at its pins just before its release commit**, once that
  upstream is published, where `builds-at-pins` could only skip it (not under `--no-wait`, nor against an
  upstream the run does not wait on, which may not be served yet). A build that fails stops the run before the
  module's release commit, with the build's errors; `--resume` builds it again, against the upstreams the stopped
  run had already finished.
- **A module its target has not served in time holds back only its dependents** and what `sluice.yml` places after
  it (or last). The other modules are released on; the run ends `STOPPED` and `--resume` waits on it again, then releases what waited.
- A run's state records each `after-tag` step done, so `--resume` after a failed step runs none of the steps before
  it again.

### Fixed

- The JitPack target's prerequisite check no longer skips a plugin whose `<prerequisites><maven>` is a property its
  parent pom sets (`maven-surefire-plugin:3.2.5`'s `${mavenVersion}`): the property is read through its `<parent>`
  poms, fetched as its own pom is.
- A refused gate's line is printed once: the command and sluice-desktop's console showed it, then the refusal that
  begins with it (`GateVerdict.repair()` is what follows the line). The `owed` refusal (under `owed: refuse`) is one
  line naming each owed module and the whole command that releases them too, by each module's alias
  (`sluice --core 1.2.0 --studio patch`), or `--no-dependents`.
- sluice-desktop reads git and files off the FX thread: each module's GitHub links and pins (Modules), the links of
  the Release and Releases boards, and a past run's state and log (Releases). The window no longer stalls on a big
  umbrella, and its background work runs on at most eight threads at once.
- After a run, sluice-desktop reads the umbrella again: the Modules tab refreshes, the Release tab's rows start over
  at the new versions (any preview dropped), and an opened Changelog tab reloads. Refresh waits while a run goes.
- sluice-desktop's Stop drops a preview still running (Preview waits until its gate ends), and a preview whose
  flags or rows changed while it ran arms nothing. Resume is checked again each time the Release tab is shown, and a state it cannot read is said.
- sluice-desktop takes a run's events in one go per frame, keeps the last 400 000 characters of its output (the
  log keeps all), and redraws a lane only when its stage, steps or errors change.

## [0.4.1] — 2026-11-22

### Fixed

- sluice-desktop's Releases tab no longer shows a run that is still going as stopped ("Stopped here; the run said
  no more about why."). A run whose state says running is live while a release holds the umbrella's lock
  (`LoggedRelease.live`); only a state with no live holder is a run that died.
- A pin move no longer fails with `versions:set-property failed … Comparison method violates its general
  contract!`. versions-maven-plugin sorts every version a repository lists, and its comparator is not consistent
  over JitPack's mix of `0.16.0`, `v0.16.0` and snapshots; every plugin run now adds
  `-Djava.util.Arrays.useLegacyMergeSort=true` to `MAVEN_OPTS`, kept beside the caller's own.

## [0.4.0] — 2026-11-21

### Added

- `sluice.schema.json`, the JSON Schema of `sluice.yml` (draft-07), so an editor checks and completes the file:
  every key, closed set and default the loader knows. `SchemaTest` holds it to `ConfigLoader`: each map's keys are
  the ones its refusal of an unknown key lists, each closed set's values the ones it accepts.

## [0.3.1] — 2026-11-17

### Added

- `asset-pins`: a JSON file in any repository of the umbrella, a module or not, that pins a module's released asset
  by hash (`{module, asset, file, bumps}`). Once a run is done, sluice waits up to 30 minutes for each released
  module's GitHub release to carry the asset, downloads it, sets the file's `version`, `url` and `sha256`, raises
  by a patch the `version` of each `bumps` file (the manifest an installed copy is updated by), and commits and
  pushes those files alone; the umbrella's pointer commit records it. A pin that cannot be written is said in the
  run's log and never stops the release: a repository off the release branch, with uncommitted changes to those
  files, or not where its origin is keeps its pin.

### Changed

- Every file states its license and copyright by REUSE (`REUSE.toml`, `LICENSES/`), every Java source starts with
  its SPDX header, and the `reuse` workflow checks both on each push. `desktop/THIRD-PARTY.txt` lists the licenses
  of the libraries sluice-desktop ships.
- Licensed under PolyForm Noncommercial 1.0.0, copyright LiQiyeDev: free for any noncommercial use, commercial use
  needs a license from LiQiyeDev. Releases up to v0.3.0 stay Apache-2.0.

## [0.3.0] — 2026-11-16

### Fixed

- A tag's packages are attached to its release and published to the package repositories again: with the tests
  skipped on a tag, `attach` and `pages` were skipped after them, so v0.2.2's release got no packages.

## [0.2.2] — 2026-11-16

### Changed

- **One install holds the command and the window.** `sluice.msi`, `sluice-windows.zip` (scoop) and the `sluice` rpm
  and deb each carry `sluice` and `sluice-desktop` on one Java runtime, cut to what both jars use. On Windows the
  window is a second launcher of the same image (`packaging/windows/sluice-desktop.properties`) and alone gets the
  Start menu entry and the desktop shortcut; scoop adds it as a shortcut. On Linux the package now depends on GTK
  for the window, and replaces the `sluice-desktop` package of 0.2.1, which the repositories no longer carry;
  `install.sh --desktop` is still accepted and changes nothing. The release's `sluice-desktop-all.jar` stays, for
  Linux x86_64 with Java 25.
- CI's test job is named *build and test*, and a tag's run no longer repeats the tests `main` already passed: the
  packages build at once. The repository variable `TEST_TAGS=true` runs them on a tag again, before the packages.

## [0.2.1] — 2026-11-13

### Added

- `desktop` (`sluice-desktop`): a JavaFX window over the library, its shaded jar
  `desktop/target/sluice-desktop-<version>-all.jar`. A start screen opens an umbrella, a folder with a
  `sluice.yml`, and keeps the recent ones; then five tabs:
  - **Modules**: each module's version on the branch, newest tag, CI, its target's build of that tag, and its pins.
  - **Release**: the command's flags and a request per module; Preview decides and gates, and prints what
    `sluice` prints; Execute… is armed only by a clean preview of the same flags and asks for a typed word. The run
    is the library's, in the window's process: a board draws each module's steps as they come, Stop stops it
    between steps, and Resume… goes on with a run that did not finish.
  - **Releases**: the runs under `releases/`, each drawn from its state beside its log.
  - **Changelog**: each module's `CHANGELOG.md` to edit, with the commits since its newest tag; Save, or Save and
    commit the file alone.
  - **Config**: the umbrella's `sluice.yml` by forms (general settings, modules, edges, gates, steps, after-release
    properties, text pins) or as YAML, one document both edit, so a form's edit changes only its lines and every
    comment stays. Beside it, the tag order and each module's edges as the library builds them from the edited
    text; under it, every problem the loader and the graph find, a click from its line. Save is refused while one
    remains; it writes the file, shows the diff and offers to commit it alone.
  The GitHub token is read as the command reads it (`GITHUB_TOKEN`, else `gh auth token`) and never shown.
- `sluice-desktop` packages: a tag builds an rpm and a deb of the window beside the command's, each with its own
  Java runtime and JavaFX inside, a menu entry and its icon; the rpm is signed like `sluice`'s. Both go into the
  signed dnf and apt repositories, and `install.sh --desktop` installs the window with the command
  (`curl -fsSL https://botmakerdev.github.io/sluice/install.sh | sudo bash -s -- --desktop`). The release also
  carries `sluice-desktop-all.jar`, for Linux x86_64 with Java 25 (its JavaFX natives are Linux's).
  `packaging/linux/build-packages.sh` builds all four packages, in CI and locally; `packaging/linux/check-packages.sh`
  installs them from a locally served signed site in Fedora and Debian containers and saves the window's screen
  under Xvfb.
- What a program around sluice needs, in `sluice-core`:
  - `ConfigLoader.check(text, label)` gives every problem of a `sluice.yml` at once (`ConfigProblem`: key path,
    message, line), YAML syntax errors included; `parse` still refuses the first one, word for word.
  - `ConfigDocument` edits a `sluice.yml` by key path (`set`, `remove`) and keeps the file as it was written:
    comments, quoting, flow or block style. An edit changes only the lines it touches; a document saved unedited is
    byte for byte the file it read.
  - `Release.preview(umbrella, requests, options)` decides and runs the gates, and tags nothing: its `Preview`
    holds the plan and the verdicts.
  - `ReleaseLogs.list(umbrella)` lists the runs under `releases/`, the newest first, each with its log, state and
    how it ended; `ReleaseLogs.read(file)` reads one run by either of its files.
  - `ModuleStatus` asks of one module what the gates ask: its newest tag, its CI on the release branch, its publish
    target's build of a release, and its pom pins against its upstreams' versions.

### Changed

- sluice is two Maven modules at one version: `core` (`sluice-core`, the library, which prints nothing) and `cli`
  (`sluice-cli`, the command and its `-all` jar). A program embeds
  `com.github.BotMakerDev.sluice:sluice-core:<tag>` from JitPack. The packages and their names are unchanged.

## [0.2.0] — 2026-11-10

### Added

- A pin in a plugin's `<artifactItem>` (what `maven-dependency-plugin` copies) is an edge like any other; its
  version moves only through a `${property}`, so a literal one is refused by name.
- `kind: ignored` in `sluice.yml` leaves a submodule out of the graph though it has a pom: the release tool's own
  submodule, say.
- `changelog: {pins: true}`: the release commit writes, under the version's `### Changed`, one line per upstream it
  now builds against (`- Built against a 1.0.1 (was 1.0.0).`), after the module's own notes. A module released
  with no change of its own (only for its upstreams) needs no notes then: those lines are its notes.
- A red `ci` names each upstream whose CI went green after the failed run: a dependent's CI builds its
  upstreams' branches, and a rerun may pass.
- One-command install on Fedora/RHEL and Debian/Ubuntu (x86_64):
  `curl -fsSL https://botmakerdev.github.io/sluice/install.sh | sudo bash`. Each tag publishes signed dnf and apt
  repositories on this repository's GitHub Pages, so later versions arrive with the system's updates; the rpm is
  signed too. On Debian and Ubuntu, whose own `sluice` is an unrelated pipe rate limiter, an apt pin makes this
  one win.

### Changed

- Untracked files are no concern of a release: `clean` no longer refuses them, and the release and snapshot
  commits stage the tracked files and what their own steps created, each named in the output, never a file that
  was untracked when that commit's work began (an editor's, a build's, another step's).

### Fixed

- An umbrella named by a relative path (the default, here) is read once: each module's git ran with its directory
  given twice, and every module came out untagged, detached and unreadable. `Runner.git` names its directory
  absolutely too, for a library caller that passes a relative one.
- A module never tagged and asked for by a level releases its branch's version (`0.1.0-SNAPSHOT` releases
  `0.1.0`), or that level above `0.0.0` when it is higher (`major` still releases `1.0.0`).
- `ci` ignores the runs of a workflow whose file is no longer in the module: its old red run says nothing of the
  branch now. GitHub's own workflows, which have no file, still count.
- `builds-at-pins` asks for a pinned upstream's repository only when the module's build fetches it: a version that
  only its `<dependencyManagement>` names is fetched by the poms that inherit it, from their own repositories. A
  bom imported there (`<scope>import</scope>`) is fetched by the module's own build, and still needs it.
- A refused run says "refused: nothing was tagged" once.

## [0.1.0] - 2026-11-10

### Added

- Versions, levels and the process runner; a preview runner that echoes every command and runs none. On Windows a
  bare program name runs by its `.exe`, `.cmd` or `.bat`, and an argument keeps the quotes inside it.
- The umbrella layout: the project's repositories read from `.gitmodules`, in its order.
- The graph: each pom read as written, the pins that move an upstream's version (a property, wherever up the
  parents it is declared; a literal; a `<parent>`), text pins and extra edges from `sluice.yml`, and the tag
  order (upstreams first, ties by `.gitmodules` order, `place: first | last | {after}`, a cycle refused by name).
- Deciding: each module's newest tag, what changed since it (a back-to-snapshot commit and moved pins are no
  change; only ignored files is its own answer; an upstream released since is a change), requests by name, level
  or version, and the dependents a release owes, listed or added with `withDependents`.
- Gates, all run before the first tag, each answering ok, skipped, forced or refused: `clean` (on the release
  branch, committed, not behind its remote), `owed`, `pins-at-main`, `text-pins`, `changelog` (the built-in reader
  or a configured extractor), `ci` (each workflow's newest finished run on GitHub), `pins-resolve`,
  `builds-at-pins` (the pom declares each pinned upstream's repository, and the module compiles at its release
  pins in an empty local repository), and a project's own commands with the release's facts in `RT_` variables.
- Publish targets: `jitpack` (the pin is the tag's name; `{jitpack: {maven: <version>}}` names the Maven its
  builds install), `{maven: <url>}` (the bare version; Central needs no declared repository, a `file:` address is
  a directory), and `none`. The wait for a tag's publish, owed only to a module a later one in the run resolves
  from a pom; JitPack's wait stops at a build it reports failed and says when Maven Central's rate limit failed
  it. The `target` gate: on JitPack, every script `jitpack.yml` runs is committed, and every pinned Maven plugin
  runs on the build's Maven, read from the plugin's own pom.
- `sluice.yml`, read strictly: an unknown key or a bad value is refused, naming where it is.
- The release itself, a preview unless asked to execute. Each module, in tag order: the release commit (its
  version, each pin at its upstream's release, the `## [Unreleased]` changelog heading stamped, the
  `before-release-commit` steps), the tag, the push of branch and tag together, a GitHub release page with the
  version's notes (`github-releases`, on by default, only with a token), the `after-tag` steps, the wait for its
  target when a later module resolves it, then back to the next snapshot: pins to their upstreams' branch
  versions, `after-release` properties set, the `after-snapshot` steps, pushed, and each dependent the run does
  not release following to the snapshot in a commit of its own. One umbrella commit at the end holds the moved
  pointers, the run's log and its state.
- Pins move through `versions-maven-plugin` (`set`, `set-property`, `use-dep-version`), a `<parent>` and a text
  pin as text, and every move is read back.
- `releases/<YYYY-MM-DD-HHMM>.json`, the run's state after every step, beside its log; resume goes on from the
  newest, a module whose target failed to build its final tag released again at its next patch.
- One release at a time per umbrella: a lock in its git directory, taken over from a run of this host that no
  longer runs, refused otherwise.
- Sync pins: each pom pin moved to its upstream's version on the branch, one local commit per module.
- `builds-at-pins` builds a module pinning by a literal or a `<parent>` too, those pins moved in the clone.
- The command line: `sluice [--umbrella DIR] (--all LEVEL | --module NAME[=VERSION|LEVEL]…) [--with-dependents]
  [--force] [--execute] [--no-wait] [--why]`, `--resume`, `--sync-pins`, `--status [FILE]` and `sluice graph`
  (the tag order, each edge and its pins). A module's alias in `sluice.yml` is a flag of its own (`--sdk 1.10.0`).
  Exit codes: 0 done or previewed clean, 1 refused, 2 stopped partway, 3 usage. Ctrl-C stops a release between
  two steps, resumable.
- Packages: `sluice-<version>-all.jar`; on a tag, CI builds an rpm and a deb carrying their own Java runtime, a
  Windows MSI, and a zip with its scoop manifest, all attached to the tag's GitHub release.
